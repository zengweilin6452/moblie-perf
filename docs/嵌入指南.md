# mobile_perf 嵌入指南（宿主接入）

面向 mobile-auto（及未来测试平台）把性能采集嵌进自有测试流程。依赖方向见
ADR-0001：宿主 → mobile_perf，本组件零第三方依赖（Python ≥ 3.10），不
import 宿主代码；设备准入由宿主注入 DeviceGate。

## 1. 术语

- **PerfKit**：组件门面（`src/mobile_perf/kit.py`）。`ensure_ready()` 巡检
  自愈；`collect()` 交互式采集窗口；`run_collect()` 定时闭环；`judge()`
  门禁判定；`trend()` 趋势对比；`leak_trend()` 泄漏趋势（跨 run 斜率，
  见 §3.1）；`save_baseline()` 基线入库。
- **DeviceGate**：短事务设备准入协议——只在发起设备命令的短窗口持有设备权，
  采集进行中不持有（与宿主整生命周期租约互补，见 §2）。
- **前台守卫**（默认开启，`PerfKit(foreground_restore=False)` 关闭）：Harness
  的 doctor/perf-start/perf-stop 经 SoloPi 控制面启动，会抢被测应用前台；
  组件在每次这类命令后检测漂移并还原为采集前组件，事件（kind=foreground）
  随 run/巡检入库。

## 2. 注入 PerfKit 与 gate 适配

```python
from mobile_perf import PerfKit
from mobile_perf.store import PerfStore

kit = PerfKit(
    serial="749622c9",          # 必填
    runs_dir="...", db_path="...",           # 建议显式，避免落进包仓库
    gate=my_gate,               # 见下；不传则默认 FileLockGate（对等参与锁文件协议）
    device_profile="Pixel7-Android14",       # 判读口径绑定，建议按机型+OS 大版本命名
)
```

宿主持有整生命周期租约时（如 mobile-auto 的 DeviceSession），注入适配器
把租约桥接为 DeviceGate——**嵌入模式重入放行**，不会与宿主互锁死锁：

```python
# mobile-auto 侧参考实现：src/mobile_auto/_perf_gate.py
from mobile_auto._perf_gate import PerfDeviceGate

gate = PerfDeviceGate(leases={serial: session._lease})   # 宿主租约预置
kit = PerfKit(serial=serial, gate=gate, ...)
```

未预置租约时适配器按短事务 acquire/release，被其他进程占用抛
`GateBusyError`（fast-fail，不排队；重试是宿主策略）。

## 3. 采集窗口（两种形态）

交互式（UI 驱动期间采集，设计方案 §6.2）：

```python
with kit.collect(target="tv.danmaku.bili", items=["CPU", "FPS", "Memory"],
                 host_run_id="pytest-20261025-001") as scope:
    drive_ui()                     # 宿主驱动被测应用
    scope.mark("scroll_done")      # 打标进统一时间轴
report = scope.report              # with 退出即 finalize（停止→pull→归档→入库→报告）
```

- 块内异常也会照常收口（端侧录制不悬挂，报告仍产出）；
- `kit.run_collect(target=..., items=..., duration_s=...)` 是同一条链路的
  定时收口特例（CLI 即用它）。

门禁判定（三态 passed / failed / not_tested；阈值归宿主，不入库）：

```python
from mobile_perf import JudgeSpec

kit.save_baseline(report, "bili-home-v3")        # 一次，基线绑定 device_profile
verdict = kit.judge(report, JudgeSpec(
    baseline="bili-home-v3",
    thresholds={"mem_pss_mb": ("lt", 220, "fail"), "fps_frame": ("gt", 50, "fail")},
))
verdict.verdict            # passed / failed / not_tested
verdict.checks             # 逐指标明细（median/op/threshold/baseline/样本数）
```

`not_tested` 的触发：报告无聚合、基线不存在、device_profile 不匹配、样本
数低于下限（默认 10，`JudgeSpec.min_samples` 可覆盖）。样本口径见
`metrics.py` 指标字典（canonical key 全组件唯一）。

### 3.1 内存泄漏趋势（跨 run 斜率）

单 run 的 median 只能说明"当时占多少"，判断是否泄漏要看同设备档案下
历史 run 的 median 是否随墙钟时间持续增长。`kit.leak_trend()` 做这件事：

```python
payload = kit.leak_trend("com.sinosoft.trainapp", profile="Xiaomi-2206123SC-Android14")
payload["runs"]          # [{runId, startedAt, durationS, median}, ...]（时间升序）
payload["slopeMbPerDay"] # OLS 斜率，单位 MB/day；样本不足时为 None
payload["confidence"]    # ok / low / insufficient
payload["runCount"], payload["spanHours"]
```

口径归组件、阈值归宿主：

- **回归方法**：普通最小二乘（OLS），横轴为 run 的 `startedAt`（墙钟小时，
  折算为"天"），纵轴为该 run `mem_pss_mb` 的聚合 median；斜率记为
  `mem_pss_slope_mb_per_day`（`metrics.METRICS` 已登记双语标签，source=analysis）。
- **样本下限**：可用 run 数默认 3（`kit.leak_trend(..., min_runs=N)` 或 CLI
  `--min-runs` 覆盖）；不足时不计算斜率，`confidence=insufficient`。
- **短跨度**：时间跨度 < 24h 仍算斜率，但 `confidence=low` 并在
  `confidenceReason` 里说明原因——不拒绝数据，也不假装可信。同一时刻的
  run（跨度为 0）无法拟合，按 insufficient 处理。
- **跨档案**：与 `kit.trend()` 完全同语义——run 跨多个 device_profile 时
  默认抛 `ProfileMismatchError`；显式传 `profile=` 只取该档案的 run，其余
  被排除时 `profileMismatch=True`（口径不一致）。泄漏判定必须同档案，否则
  内存基线差异会伪装成斜率。

宿主阈值判定（三态，同 judge 语义）：

```python
payload = kit.leak_trend("com.sinosoft.trainapp", slope_threshold=2.0)  # MB/day
payload["verdict"]["verdict"]   # slope > 2.0 → failed；样本不足 → not_tested
```

也可单独调用纯函数 `mobile_perf.leak.leak_verdict(analysis, threshold=..., level="warn")`：
`level="fail"` 拉低结论，`level="warn"` 只记 warnings；低置信度斜率照常判定，
置信度说明进 `warnings`。CLI 等价：

```bash
mobile-perf leak com.sinosoft.trainapp --profile Xiaomi-2206123SC-Android14 \
    --slope-threshold 2.0 --level warn
```

实践建议：泄漏趋势至少跨数天采集（每天一轮），否则 `confidence=low` 的斜率
只适合做冒烟提示，不适合当发布门禁。

### 3.2 弱网与逐帧（M6）

弱网剖面、逐帧采集与整页加载耗时是三个**独立开关**，任一环境缺席各自降级、
互不阻断（逐项降级语义见 ADR-0004 与 GLOSSARY「降级链」）：

```python
with kit.collect(target="tv.danmaku.bili", items=["CPU", "FPS", "Memory"],
                 frame_poll=True,                    # 逐帧 P50/P90/P99（工单 15）
                 net_profile="weak",                 # 弱网档位（工单 17）
                 net_tier="passthrough",             # decrypt=接口级（工单 18）
                 ) as scope:
    drive_ui()
    scope.mark_page("home")                          # 页面起点（工单 19）
report = scope.report
```

- **逐帧**（`frame_poll=True`）：gfxinfo framestats 的逐帧耗时分布；
  `net_conn_duration_ms`、`app_frame_*` 不可用时在 `metricsSummary` 里如实
  `notTested` 并给原因，绝不产 0 值。
- **弱网**：档位名（none/4g/3g/weak/custom）在采集窗口前施加、退出必恢复
  （异常退出后跑 `mobile-perf netprof doctor` 复验清理）。是否真的生效只看
  代理侧证据，`report["network"]["effective"]` 为准。
  - **要测首屏就必须在窗口内冷启动 App**：窗口外起 App 的话，首屏请求在代理
    施加前已经直连发完，代理侧一条连接都没有——`applied=true` 但
    `effective=false`，档位等于没生效（真机实测：窗口外 0 连接 / 窗口内 23 个）。
  - **弱网整形只作用于 CONNECT 隧道**：明文 HTTP 不做延迟/带宽整形，验证弱网
    机制请用 HTTPS；但 `--capture-har` 的 HAR 写入不受此限，明文 HTTP 也会记录
    （见 3.3）。
  - mitmproxy 是可选依赖，需 Python ≥3.12，且要与被测设备可达（`adb reverse`
    已由组件建立）。找不到时 `net_conn_duration_ms` 如实 `not_tested` 并附安装
    提示；装好后用 `MOBILE_PERF_MITMDUMP=<mitmdump 路径>` 或
    `--net-mitmdump` 指定（Windows 下 `pip --user` 装到用户脚本目录，通常不在
    PATH）。
- **整页耗时**（`mark_page` + `frame_poll`）：从页面打标到画面视觉稳定的
  耗时（`page_load_ms`）。帧完成时刻是设备 `CLOCK_MONOTONIC`，与宿主时间轴
  不同源，换算靠**逐帧轮询自己的锚点**：每轮把宿主会话时刻中点与该轮最新帧
  时刻配对，取全部候选的最小值（空闲轮只会让候选偏大）。`report["pages"]`
  里 `clockOffsetSource=frame_anchor`、`clockAnchorCount` 给锚点数、
  `clockPrecisionMs` 给可信度（半个 adb 往返，整页值上的常数偏置不超过它）；
  没有可用帧时刻就整页 not_tested，不拿错位时刻硬算。
  不要改用 `/proc/uptime`：那是 `CLOCK_BOOTTIME`（含休眠），真机实测差
  285734 s，会把所有帧推到页面起点之前，整页全部误判成"没有帧"。
- **可比性**：网络档位是与设备档案并列的维度。`kit.trend` / `kit.leak_trend`
  跨档位默认拒绝，显式传 `net_profile=` 过滤并把被排除档位标成
  `netProfileMismatch=True`；`kit.judge` 从基线来源 run 解析档位，与本次
  run 不同 → `not_tested`（口径不可比，这是设计行为不是故障）。
- CLI 等价：`mobile-perf collect <pkg> --net-profile weak --frame-poll`、
  `mobile-perf trend <pkg> --metric mem_pss_mb --net-profile weak`；
  `scripts/perf_full_flow.py --net-profile weak --net-mitmdump <路径> --pages home,detail`
  跑弱网两轮对比（两轮都在采集窗口内冷启动；第一轮无弱网对照，跨档位不进门禁、
  逐指标并排对照）。巡检未通过但只需看采集结果时加 `--allow-degraded`。

### 3.3 APP 抓包（HAR，默认关）

抓包与弱网是**正交**的两件事：`capture_har=True` 且未给 `net_profile` 时，
组件仍会起 mitmproxy（内部 `none + decrypt`），但 `sessions.net_profile` 保持
`None`，报告 `network.captureOnly=true`；给了 `net_profile` 则沿用原档位，
`net_tier` 必须为 `decrypt`，否则 `ValueError`（CLI exit 1），不会偷偷改档。

```python
from mobile_perf.har_writer import CaptureOptions

options = CaptureOptions(
    enabled=True,
    capture_bodies=False,          # 默认只记 size + MIME + sha256
    body_limit_bytes=65536,
    max_entries=5000,
    max_bytes=67108864,
    max_hash_bytes=8 * 1024 * 1024,  # 超过该字节数不计算 sha256（默认 8 MiB）
    redact=True,                   # 默认脱敏；关闭仅限本地排查
)
with kit.collect(target="tv.danmaku.bili", items=["CPU"],
                 capture_har=True, net_tier="decrypt",
                 capture_options=options) as scope:
    drive_ui()
report = scope.report
har = report["network"]["har"]      # 状态/条目/脱敏/截断/不可用原因摘要
```

CLI 等价：

```bash
mobile-perf collect <pkg> --items CPU,Memory --duration 30 \
  --capture-har --net-tier decrypt --net-mitmdump <mitmdump 路径>
mobile-perf report <runId>          # report.html / report.json 内含 network.har 摘要
```

真机不安装 CA 的双路径验收、报告检查点与已知边界见
[docs/app-har-capture-acceptance.md](app-har-capture-acceptance.md)。正式包
证书拒绝时只能验证降级路径；不要把明文 HTTP 的 `partial` HAR 误读为
HTTPS 已解密。

- 产物：`runs/<runId>/network/app.har`（合法 HAR 1.2）与流式
  `app.har.entries.jsonl`；addon 逐行 append+flush，`stop()` 在设备恢复且
  **代理进程确认终止后**流式合成并原子替换，Windows 硬终止不丢已写条目；
  终止失败时本次不合成（避免漏掉进程续写的条目），状态与引用保留，
  下一次 `stop()` 重试终止成功后再合成（生命周期复核缺口，见 ADR-0005）。
- 报告：`report.json`/`report.html` 只带 `network.har` 摘要与相对链接
  `network/app.har`，**不内嵌正文或敏感原值**；旧 run 无 `har` 键时报告零变化。
- 降级（均不阻断采集）：
  - mitmproxy 缺失 / 端口占用 / 代理未起 / 零 HTTP 请求 → `status=not_tested`
    并写原因，**不创建空 `app.har`**；
  - App 不信任代理 CA 但存在明文 HTTP → `status=partial`、
    `httpsCoverage="none"`、`notTestedReason` 明写 HTTPS 未解密；CONNECT 不写成请求；
  - 条目/字节上限触发 `partial`（`truncated`/`droppedEntries`），writer 失败只记
    `har_error` 事件，代理继续转发；
  - 计数口径（P0-03/P0-04）：`har_dropped`/`har_error` 事件按"首次 + 每累计
    100 条"节流落日志（`dropped`/`errors` 字段为当时的累计数），防止磁盘满或
    限额触顶时把唯一的代理证据日志灌成事件流；精确计数由 writer 旁路状态文件
    `network/app.har.entries.jsonl.state.json` 承载（常驻句柄就地重写并
    flush，进程硬杀不丢已 flush 内容；单条开销 ~0.01 ms，修复前逐条
    临时文件+原子替换实测 ~1.16 ms/条）。
    摘要里 `droppedEntries`/`writerErrors` 优先取状态文件精确值
    （`countersSource="writer_state"`）；无状态文件时（旧 run/状态损坏）退回
    日志推算，为下界（`countersSource="proxy_log"`）。`droppedEvents` 是节流
    日志事件条数，与 `droppedEntries`（真实丢弃条目数）不是同一口径。
- 覆盖边界：HTTPS 需 App 信任代理 CA；QUIC/UDP、非 HTTP TCP、pinning 与未关闭的
  WebSocket 长连接不保证覆盖。抓包不参与 `net_conn_duration_ms` / `api_*` 计算，
  `net_proxy.jsonl` 仍是代理生效的唯一证据。
- 脱敏覆盖边界（P1-02）：默认名单覆盖常见认证头（authorization/cookie/token 等
  14 个）、认证类查询参数（token/session/password/sign 等 24 个）、URL 型头
  （Referer/Location/Content-Location/Refresh，含 Refresh 的 `N; url=` 前缀与
  fragment 内的键值对——OAuth 隐式流的 `#access_token=` 场景）与 userinfo。
  **业务自定义敏感字段（如业务侧 session key、身份证号、手机号参数名）不在默认
  名单内**；本轮未提供扩展配置项——若被测 App 的敏感参数名不在上述名单中，
  要么改名、要么在代理层前置过滤，不要假设产物里没有该值。关闭脱敏
  （`redact=False`/`--capture-har-no-redact`）仅限本地排查，报告会显著标注危险。

## 4. pytest 钩子 `--mobile-perf`

本包装后（entry point `pytest11: mobile-perf`）即提供 `perf` fixture，形态
对称 mobile-auto 的 `--mobile-evidence`。opt-in：不开旗标零行为。

```python
def test_home_scroll(device, perf):
    with perf.session("tv.danmaku.bili", items=["CPU", "Memory"]) as scope:
        device.launch_app("tv.danmaku.bili"); device.swipe_up(5)
        scope.mark("scroll_done")
    # 退出即 finalize；指定 baseline 时自动 judge
```

- 结论经 `report.sections`（标题 `mobile-perf`：runId/durationS/verdict/
  逐检查项）进 JUnit/HTML 等报告；阈值判 failed 不拉低用例结论——由宿主
  对 `perf.results[-1].verdict` 断言决定；
- `perf.results` 为本用例全部采集结果（`PerfResult.report/.verdict`）；
- serial / 采集项 / 基线 / 阈值经 CLI 或 ini：

  | 参数 | CLI | ini |
  |---|---|---|
  | 开关 | `--mobile-perf` | — |
  | serial | `--mobile-perf-serial` | `mobile_perf_serial` |
  | 采集项 | `--mobile-perf-items CPU,FPS,Memory` | `mobile_perf_items` |
  | 基线 | `--mobile-perf-baseline NAME` | — |
  | 阈值 | `--mobile-perf-threshold METRIC:OP:LIMIT:LEVEL`（可重复） | `mobile_perf_thresholds`（逗号分隔） |
  | 归档目录 | `--mobile-perf-runs-dir` | — |
  | store 路径 | `--mobile-perf-db` | — |

  OP ∈ lt/le/gt/ge，LEVEL ∈ fail/warn。session 调用参数
  （`perf.session(target, items=..., baseline=..., thresholds=...,
  min_samples=...)`）优先于 CLI/ini。

- **kit 替换点**：`mobile_perf_kit` fixture（session 级）是唯一构造入口，
  宿主 conftest 同名覆盖即可注入自家 adb 路径、DeviceGate 适配器、
  device_profile 与共享 store——mobile-auto 的真机联动用例
  （`tests/device/test_perf_linkage_device.py`）即按此覆盖。

## 5. 并发（pytest-xdist）

- 设备准入：同设备两 worker 并发采集 → 后到者在首个设备命令上收到
  `GateBusyError`（fast-fail，实测秒级完成、不死锁）；不同设备 → 各自
  独立成跑；
- store：SQLite WAL + busy_timeout 5s，多进程并发首连与写入安全
  （journal_mode 切换竞争已内置重试）；
- runs 目录建议按 worker 分目录（mobile-auto 池化的
  `worker_artifacts_dir` 即此语义），store/lease 目录可共享。

## 6. 已知边界

### 6.1 PC 补采指标的机型适用性与可比性（P1-06）

| 指标 | 数据源 | 采样 | 已知机型差异与降级 |
|---|---|---|---|
| `app_thread_count` | `cat /proc/$(pidof <pkg>)/status` 的 Threads 行 | 随补采轮询间隔（默认 2 s） | pid 不唯一（多进程 `:push`/`:remote`）→ 不猜主进程，`degraded`；读不到 → None 不伪造 0 |
| `app_fd_count` | `ls -1 /proc/<pid>/fd` 计行 | 同上 | shell 权限受限机型（Permission denied 并入 stderr）→ None；空输出按读不到处理，不是 0 |
| `device_thermal_status` | `dumpsys thermalservice` 状态行（0–6） | 同上 | 老版本 Android 无该服务 → None；**0 档是有效读数**（无热节流），不是缺失 |
| `cpu_freq_max_mhz` | `cat /sys/.../scaling_cur_freq`（kHz→MHz 取最大） | 同上 | 部分机型限制 shell 读 sysfs → cat 段为空 → None |
| `gpu_util_pct` | `kgsl gpubusy` 比值 → `dumpsys gpu` → not_tested 三级链 | 同上 | 仅 Adreno 机型 shell 可读 kgsl；`0 0` 语义按机型不同（M6 方案 §2.1a 两台真机实测），绝对值**不可跨机型比较** |
| `gpu_mem_mb` | `dumpsys gpu` 的 `Proc <pid> total` 字节数（1024² 换算 MB） | 同上 | 多 pid 时取唯一 pid 才采，多进程应用如实降级 |

可比性口径：

- **可跨版本比较**：`app_thread_count`、`app_fd_count`、`cpu_freq_max_mhz` 数值
  语义明确（计数/频率），但强依赖被测 App 版本与运行状态，跨 App 版本无可比性；
- **必须同设备档案比较**：`gpu_util_pct`（比值语义随机型/窗口常量变化）、
  `device_thermal_status`（档位阈值随厂商温控策略不同）、帧率类（刷新率绑定设备）；
